# Field test: 0.6.81 dual core on a real FM-1

Tested on 14 Oct 2026 on one M-VAVE FM-1. This is a measurement report only, with no code changes.

- **Firmware:** `v0.6.81-a6e33a3-preview`, the package from the preview channel of the project site (identity FM-1_900),
  SHA-256 `3990c248e05c1c6e130c6ea423edf7fc2f42075825f9c9f4ac2f256310aad2b5`.
- **Install:** official V15 (FM-1_015), then JIANT with `tools/fm1_install.py`.
- **Measured with:** the USB console. `status` was read about every 5 s; `status`, `crash` and `dbg` at the start and the end of each run.

## Result

- `cpu2 CORES 2` on both normal boots after install. No fault, `fx_trips 0`, `no crash record`, `boots 1`.
- With the same song, two cores brought core 0 load from 52 % to 37 % (mean), and the overload guard never fired.
  On one core it faded 451 voices in 3 minutes.

## Same song, one core vs two

One saved 4-track song at 140 BPM, loaded right after power-on and left playing for three minutes with no edits, once per mode:
run C with REC held at power-on (`CORES 1 (REC AT POWER-ON)`), run D with a normal power-on (`CORES 2`). BPM was checked at
every read and stayed at 140. Counters are the increase over each window; `audio_max_us` is the worst half since power-on.
A half is 128 frames at 44.1 kHz, so 2902 µs is the limit, and the guard fades a voice when two halves in a row go above 80 % (2322 µs).

| 3 minutes, same song | C: 1 core | D: 2 cores |
|---|---:|---:|
| core 0 load (`cpu_pct`), mean / peak | 52 % / 70 % | 37 % / 51 % |
| `audio_max_us` since power-on | 2753 (95 %) | 2129 (73 %) |
| `voices_shed` | +451 | 0 |
| `voices_given_up` | +538 | +104 |
| `audio_late` | +1 | 0 |
| `cpu2_wait_max_us` | - | 262 |
| `fx_trips` / `crash` | 0 / no crash record | 0 / no crash record |

On one core the guard fades about 2.5 voices a second on this song, which keeps `audio_late` low. On two cores the worst half
stays under the 80 % threshold, so the guard never fires.

## What core 1 did (run D)

`cpu2_tracks` was 0 in 27 of 36 reads, track 2 in 7, track 1 in 1, tracks 1 and 2 in 1. Core 1 also runs the buses in every
block (`MC_FX`, 0.6.75), so `cpu2_tracks 0` does not mean idle: the drop on core 0 comes mostly from the buses.
`cpu2_jobs` rose steadily at about 1,380 blocks per second.

## Also found: two host tests fail on macOS

On a clean 0.6.81 checkout, `./build.sh` passes and `tests/run_tests.sh` fails only two cost checks:

- `mod: 4 active slots add at most a few percent`: +3.4 % on the GRAIN part (1602 -> 1636 instructions / sample);
- `reverb: cost: the reverb alone ROOM 93, SPRING 160 instructions / sample (+72 %, limit +30 %)`.

Both count instructions with `proc_pid_rusage`, which exists only on macOS (Apple clang 21), so on Linux these checks are
skipped and never run.
